# Cortex-M 程序运行机制
## 1. Thread Mode 与 Handler Mode
Cortex-M 处理器存在两种基本执行模式：
- **Thread Mode**：用于执行普通程序代码，例如 `main()` 和 FreeRTOS 任务。
- **Handler Mode**：用于执行异常和中断处理程序，例如 IRQ、SysTick、PendSV、SVC、HardFault 等。
处理器当前处于哪种模式，由 **CPU 是否正在处理异常（Exception）** 决定：
- `IPSR = 0`：Thread Mode
- `IPSR != 0`：Handler Mode
正常程序运行时 CPU 处于 Thread Mode；发生异常后，Cortex-M 硬件自动进入 Handler Mode；执行异常返回后，再恢复到 Thread Mode。

### 1.1 Thread Mode
Thread Mode 可以是：
- **Privileged（特权）**: 可以访问所有普通资源以及受权限限制的系统资源，可以修改大部分特殊寄存器，并执行需要特权权限的操作。操作系统内核、底层系统代码通常运行在特权级。
- **Unprivileged（非特权）**: 访问权限受到限制，不能直接执行部分系统控制操作，也不能随意修改某些特殊寄存器。通常用于限制普通应用或任务，避免单个任务错误影响整个系统。

Thread Mode 可以使用：
- **MSP（Main Stack Pointer）**
- **PSP（Process Stack Pointer）**
具体由 `CONTROL` 寄存器控制：
- `CONTROL.nPRIV`：控制 Thread Mode 是特权还是非特权。
- `CONTROL.SPSEL`：控制 Thread Mode 使用 MSP 还是 PSP。
在 FreeRTOS 中，普通任务通常运行在：`Thread Mode + PSP`

### 1.2 Handler Mode
Handler Mode 用于执行中断和异常处理程序，并具有两个固定特点：
- ***始终为 Privileged（特权模式）***
- ***始终使用 MSP***

因此 FreeRTOS 中典型的执行过程为：

```text
Task A
Thread Mode + PSP
    ↓
发生 PendSV / SysTick / IRQ
    ↓
异常处理程序
Handler Mode + MSP
    ↓
异常返回
    ↓
Task A 或 Task B
Thread Mode + PSP
```

### 1.3 Thread Mode 与任务状态的区别
***Thread Mode / Handler Mode 是 Cortex-M CPU 的执行模式，而 Running / Ready / Blocked / Suspended 是 FreeRTOS 的任务状态，两者不是同一个概念。***

例如：

```text
Task A = Running
CPU = Thread Mode
```

如果此时发生中断：
```text
Task A 原本处于 Running
CPU 原本处于 Thread Mode
    ↓
发生中断
    ↓
CPU 进入 Handler Mode
    ↓
执行 ISR
    ↓
异常返回
    ↓
CPU 回到 Thread Mode
```

因此可以简单记为：
> ***没有异常正在执行 → Thread Mode；正在执行异常或中断 → Handler Mode。***

## 2. RAM 默认布局与标准 C heap

STM32/GCC 常见链接结果：**低地址是 `.data`，接着 `.bss`，主栈在 `_estack`（RAM 最高处）向下长。** 标准 C heap 不是启动文件里拷贝或清零出来的一段，而是 `.bss` 结束后用 `_end` 标出起点，第一次 `malloc` 时才经 `_sbrk` 往上长。

```text
高地址
_estack                         向量表第 0 项，复位后 MSP 初值
┌─────────────────────────────┐
│ 主栈（MSP）                  │  局部变量、调用栈、ISR
│ 从 _estack 向下长            │  链接期至少留 _Min_Stack_Size
├─────────────────────────────┤
│ 中间空隙                     │  栈向下、C heap 向上，两边都能长进去
│ 标准 C heap（malloc/free）   │  从 _end 向上长
│                             │  链接期至少留 _Min_Heap_Size
├─────────────────────────────┤
│ .bss 未初始化全局/静态       │  含 FreeRTOS 的 ucHeap[]（若用 heap_4）
│ .data 已初始化全局/静态      │  从 Flash 拷到 RAM
└─────────────────────────────┘
低地址
```

### 2.1 ld 与启动文件里 C heap 在哪

ld 文件开头通常有 `_estack`、`_Min_Heap_Size`、`_Min_Stack_Size`。`SECTIONS` 里 `.data` 后接 `.bss`，再跟一段不会生成可加载内容的占位：

```ld
._user_heap_stack :
{
  PROVIDE ( end  = . );
  PROVIDE ( _end = . );       /* C heap 起点：.bss 后第一个空闲地址 */
  . = . + _Min_Heap_Size;
  . = . + _Min_Stack_Size;    /* 链接期容量检查，不是运行时两块贴死的专属区 */
} >RAM
```

`_Min_Heap_Size` / `_Min_Stack_Size` 是**至少**：`.data` + `.bss` 放完后还塞不下这两段，链接直接失败。ld 里一般没有 `_Max_Heap_Size`。运行时 C heap 的上限由 `_sbrk` 决定：CubeMX 的 `sysmem.c` 把堆顶限制在 `_estack - _Min_Stack_Size`，即给主栈至少留 `_Min_Stack_Size`，所以能 `malloc` 的总量约为 `_estack - _Min_Stack_Size - _end`；RAM 有空余时，这个量可以远大于 `_Min_Heap_Size`。没人 `malloc` 时这块可以一直是空的。

`startup_stm32xxxx.s` 的 `Reset_Handler` 只做：把 `.data` 从 Flash 拷到 RAM、把 `.bss` 清零、向量表第 0 项加载 `_estack`。不初始化 C heap。真正推动堆顶的是 newlib 的 `_sbrk`（CubeMX 工程常在 `syscalls.c` / `sysmem.c`）。

三套内存不要混：

| | 谁用 | 在哪 |
|--|------|------|
| 局部变量、函数参数、返回地址 | 栈 | 启动前是 MSP 主栈；任务跑起来后是该任务 PSP 栈；中断里始终是 MSP 主栈 |
| `malloc` / `free` / C++ `new` | 标准 C heap | `_end` 往上，`_sbrk` |
| 全局 / `static` | `.data` / `.bss` | 含 `ucHeap[]`。`pvPortMalloc` 走这块数组，不是标准 C heap |

各段放在哪块 RAM（H743 的 DTCM 或 AXI SRAM）由 `.ld` 的 `MEMORY` / `SECTIONS` 决定，可以改。但不能当成积木任意对调：栈向下、C heap 向上，对调后要一起改 `_sbrk`；`_estack` 必须跟着真实栈顶走。H743 的 DTCM 只有 128KB，且普通 DMA1 / DMA2 访问不到（只有 MDMA 能），很多工程是栈在 DTCM、`.data` / `.bss` / `ucHeap` 在 AXI SRAM。

FreeRTOS 任务、队列等动态对象见 [动态创建任务的内存管理](../freertos/04_freertos之task.c--任务创建与内存管理.md)。
