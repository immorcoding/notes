# 存储：从文件读写到 FatFs、FTL 与 Flash 的完整链路

> 本文结合 MP3 工程 version0.4.0 的 NOR Flash 存储实现，解释文件、逻辑扇区、地址映射、同步、删除、掉电恢复与垃圾回收之间的关系。
> 工程相关参数按 2026-09-01 的代码核对。文中的示意地址、文件和时序用于理解机制，不是实际分区布局或硬件测速结果。
> 本文使用二进制单位：1 KiB = 1024 B，1 MiB = 1024 KiB。平时口头说的“4 KB 块”和“3.5 KB 方案”，这里分别写作 4 KiB 和 3.5 KiB。

如果主要想弄清“删除文件以后，空间到底怎么释放”，先读第 11～13 节的完整例子，再看第 14 节 GC。整体分层和地址转换见第 2～7 节；同步等待见第 9～10 节；掉电恢复与格式化见第 15～17 节。

## 1. 为什么存一个文件需要这么多层

应用想做的事情很简单：把一段数据写进文件，之后按文件名读回来。

但 NOR Flash 芯片只认识地址、读命令、页编程命令和擦除命令。它不知道什么是文件，也不知道某段数据已经被删除。

中间各层负责把不同含义逐步翻译：

```text
应用：把这些字节写入 config.bin
                 ↓
文件系统：这个文件占哪些簇？修改哪些数据扇区、FAT 表和目录项？
                 ↓
逻辑块接口：从 LBA x 开始，读/写 n 个 512 B 扇区
                 ↓
FTL：这些 LBA 当前存在哪里？新版本放哪个空闲物理块？
                 ↓
Flash 驱动：在芯片地址 y 编程一页，或者擦除一个 4 KiB 块
                 ↓
控制器与芯片：传输命令、搬运数据、完成内部擦写
```

**每一层维护的是不同的信息。** 理解存储时，最容易出错的地方是把不同层都叫作“块”，又把不同层的“空闲”“成功”“同步”当成同一件事。

例如，“文件系统认为这片空间可以分配给新文件”，并不代表“Flash 上对应位置已经擦成全 0xFF”。

## 2. 先分清六种单位

| 名称 | 当前工程中的大小或含义 | 谁负责理解 |
| --- | --- | --- |
| 文件字节 | 应用可以请求读写任意数量的字节，例如 100 B | 应用、Filesystem Service、FatFs |
| FatFs 逻辑扇区 | 固定 512 B，以 LBA 编号 | FatFs、DiskIO、FTL |
| FAT 簇（Cluster） | 若干连续逻辑扇区；每簇扇区数在格式化时确定 | FatFs |
| FTL 逻辑组（Group） | 固定 7 个逻辑扇区，即 3584 B = 3.5 KiB | FTL |
| NOR 物理擦除块 | 4096 B = 4 KiB；本方案一个组版本独占一块 | FTL、底层 Flash 驱动 |
| NOR 编程页（Page） | 256 B 页边界；当前 FTL 按页提交编程 | Flash 驱动、FTL 记录布局 |

### 2.1 LBA 是逻辑编号，不是芯片地址

LBA 是 Logical Block Address，当前每个 LBA 对应 512 B。

```text
LBA 140：逻辑盘中的第 140 号扇区
LBA 141：逻辑盘中的第 141 号扇区
```

FatFs 只需要知道这些扇区可读写，不需要知道它们位于 NOR 的哪个物理块。

有了 FTL，同一个 LBA 今天可以映射到物理块 P_A，下一次改写后可以映射到 P_C。应用和 FatFs 仍然使用同一个 LBA。

### 2.2 FAT 簇和 FTL 逻辑组不是一回事

FAT 用“簇”给文件分配空间。例如，假设一个卷格式化后每簇 8 个扇区：

```text
一个 FAT 簇 = 8 × 512 B = 4096 B
一个 FTL 组 = 7 × 512 B = 3584 B
```

两者大小不同，边界通常也不一致。一个 FAT 簇可能跨两个 FTL 组；一个 FTL 组也可能同时包含不同文件的数据，甚至跨过文件系统内部区域的边界。

**不能因为底层使用 4 KiB 擦除块，就推断 FatFs 的簇一定是 4 KiB；也不能把每簇设置成七个扇区来迁就 FTL。** 当前 FAT 簇的扇区数遵循文件系统的二次幂约束，七扇区分组只是 FTL 内部实现。

本文后面的 4 KiB 文件示例会明确假设“每簇八扇区”，不表示当前工程格式化后一定得到这个簇大小。

### 2.3 “空逻辑单元最小是多少”要拆开回答

- FatFs 对块设备发出的最小读写单位是 512 B。
- FTL 映射和更新的单位是一个 3.5 KiB 逻辑组。
- FTL 为一个新组版本分配的物理空间是一个 4 KiB 擦除块。
- 256 B 是编程页的边界，不是当前 FTL 的独立分配单位。

因此，本方案不会在同一个 4 KiB 块里把几个 256 B 空页分别分配给不同组版本。

## 3. NOR Flash 为什么不能像 RAM 一样随便覆盖

### 3.1 擦除后的值是 0xFF

NOR 擦除后各位为 1，因此字节读出来是：

```text
11111111 = 0xFF
```

编程可以把位从 1 改为 0；需要从 0 变回 1 时，必须先擦除所在擦除块。

```text
擦除后：11111111
编程后：10110000

若希望变成 11110000：
中间存在 0 → 1，不能直接靠再次编程完成
```

所以，“空白 Flash 是全 0，可以随便写”这个理解不对。全 0 的字节反而已经没有可继续清零的位。

### 3.2 页编程和块擦除的粒度不同

芯片编程受 256 B 页边界限制，擦除则以支持的擦除单位进行。本工程 FTL 使用 4 KiB 擦除。

即使只想修改几个字节，也不能把任意已有数据直接覆盖到原位置。还要考虑其他字节是否需要保留，以及操作中断后是否还能找到旧数据。

当前 FTL 进一步约束：**新块的每一页在一个擦除周期内最多编程一次。** 提交记录放在单独的一页，最后写入，不依赖反复改写同一个状态字段。

### 3.3 为什么 SD 看起来没有这个麻烦

SD 卡里面已经有控制器，控制器负责把主机看到的逻辑扇区转换到卡内部 Flash，并处理相应映射和回收。

```text
SD 路径：
FatFs → SD DiskIO → SDCard Component → SDMMC → SD 卡控制器 → 卡内 Flash

原始 NOR 路径：
FatFs → USER DiskIO → MCU 上的 FTL → W25Qxx → NOR Flash
```

因此 MCU 上的 SDCard Component 不必再实现本文这套 NOR FTL，但它仍然承担 SD 协议与设备访问职责，并不是整个 Component 层都被省略了。

## 4. 当前工程的完整调用链与每层职责

### 4.1 一次文件操作的请求方向

```text
APP / StorageTask
    │ 决定何时保存、测试、维护，以及如何处理结果
    ▼
Filesystem Service 的文件接口
    │ 持有文件对象，检查上下文、句柄、挂载状态
    ▼
FatFs：f_open / f_read / f_write / f_sync / f_close / f_unlink
    │ 把文件和元数据操作转换为逻辑扇区操作
    ▼
FatFs disk_* 分发 → CubeMX USER DiskIO
    │ user_diskio.c 的 USER CODE 区薄转发
    ▼
bsp_driver_user_diskio 契约
    │ BSP_USER_DISKIO_*，最终链接到 Service 提供的强定义
    ▼
Filesystem Service 的 Flash 块后端与同步执行器
    │ 参数/状态转换，发起操作，等待通知，推进状态机
    ▼
Platform Flash
    │ 装配实例、分区、工作内存、映射模式及生命周期
    ▼
Flash FTL Component
    │ LBA 映射、组更新、CRC、提交、恢复、GC
    ▼
FlashFTL_RawOps → FTL/W25Qxx Bridge
    │ 转换操作/状态，把分区内相对地址转换为芯片地址
    ▼
W25Qxx Component → BusOps → STM32 HAL QSPI Adapter
    │ 芯片协议、页编程/擦除、WIP 等待、控制器和 DMA
    ▼
QSPI 控制器 → NOR Flash
```

Service 在图中出现两次，因为它同时提供两个不同方向的接口：上面是应用使用的“文件服务”，下面是 FatFs 所需的“块设备后端”。这不意味着 FTL 又反过来调用文件系统。

### 4.2 编译依赖与运行调用要分开看

`FATFS` 属于中间件及其适配区域，不应该直接包含 Service 的业务头文件。

本工程采用的办法是让中间件依赖自己的后端契约：

```text
FATFS/Target/bsp_driver_user_diskio.h
    声明 BSP_USER_DISKIO_* 契约

FATFS/Target/bsp_driver_user_diskio.c
    提供弱默认实现；没有实际后端时安全失败

Service/filesystem/flash/filesystem_flash_bsp.c
    包含上述契约，提供同名强实现
```

运行时会执行 Service 的强实现，但生成的 USER DiskIO 不需要知道 Service 的私有结构，也不需要包含 Service 头文件。

弱定义必须返回未就绪或错误，不能在没有读写任何东西时返回成功。还要确认强实现确实进入最终链接结果；只把它丢进某个未被提取的静态库，并不能保证覆盖弱定义。

### 4.3 CubeMX 负责什么

当前工程使用的 CubeMX User-defined 配置生成了 `user_diskio.c/.h` 骨架。`bsp_driver_user_diskio.c/.h` 是工程自行维护的契约文件，不是 CubeMX 自动生成的 NOR 后端。

生成文件只在 USER CODE 区接入契约转发；FTL、等待、日志和 GC 不塞进生成模板。重新生成后应检查 USER CODE 是否保留，以及自维护源文件是否仍参与构建。

两个卷的路径使用生成链接结果 `SDPath`、`USERPath`。SD、USER 都链接成功且顺序不变时，常见结果分别是 `0:/` 和 `1:/`，但代码不能据此硬编码。

**全局卷号和驱动内 LUN 不同。** USER 卷可能使用 `1:/`，传给当前 USER 后端的驱动内 LUN 仍是 0。

### 4.4 各层不应该做什么

| 层 | 应负责 | 不应承担 |
| --- | --- | --- |
| APP / StorageTask | 业务编排、测试时机、维护机会 | 新文件流程不绕过 Service 直接访问 FatFs/FTL |
| Filesystem Service | 文件对象、卷流程、后端实现、任务等待 | 不实现物理映射、组提交算法 |
| FatFs | 文件、目录、FAT 簇链、逻辑扇区 | 不管理 NOR 失效块和 GC |
| Platform | 实例、内存、分区、设备装配与生命周期 | 不解释 FAT，也不实现 FTL 记录算法 |
| FTL | 逻辑组映射、提交、扫描、分配与 GC | 不包含 HAL、FreeRTOS、FatFs、W25Qxx 依赖 |
| Bridge | 两个 Component 的接口、状态与地址转换 | 不调度任务，不另做 GC |
| W25Qxx / HAL Adapter | 芯片命令与硬件操作 | 不识别文件名、簇、文件删除 |

Service 内部按 `sd/`、`flash/` 划分各自后端；对应用仍由 Filesystem Service 的公开接口提供能力。

## 5. 文件系统到底把什么存进了逻辑盘

一个文件除了内容，还需要描述“它叫什么、在哪里、长度多少”的元数据。

以 FAT12/16 的基本结构理解：

```text
FatFs 所见的逻辑盘
├── 卷引导/参数区域：每扇区字节数、每簇扇区数、区域位置等
├── FAT 表：簇的分配状态和簇链
├── 根目录等目录结构：文件名、起始簇、文件长度、属性等
└── 数据区：文件内容，以及需要使用簇保存的目录内容
```

例如一个文件占用三簇：

```text
目录项：demo.bin，起始簇 = 12，长度 = 9000 B

FAT[12] = 25
FAT[25] = 26
FAT[26] = 簇链结束标记

文件内容依次位于：簇 12 → 簇 25 → 簇 26
```

簇号不连续也可以，因为 FAT 表保存了链关系。应用读文件时，FatFs 会沿着链找到对应扇区。

**FAT 表、目录项和文件内容最终都是逻辑扇区里的字节。** 它们写入 NOR 时，全都会经过同一个 FTL。FTL 不知道某次写入是在修改 FAT 表，还是在保存 MP3 数据。

### 5.1 文件占用空间与 FTL 物理占用不能混算

一个 100 B 文件可能占用至少一个 FAT 簇，而不是恰好 100 B，也不一定只是 512 B。

底层第一次落盘时，又可能涉及文件数据所在的逻辑组、FAT 表所在的逻辑组、目录所在的逻辑组。因此，不能简单说“100 B 文件原来占 512 B，现在只占一个 4 KiB 块”。

要分别计算：文件长度、文件系统分配的簇、FTL 保存的组版本、尚未回收的旧版本。

## 6. 3.5 KiB 方案怎样放进一个 4 KiB 块

### 6.1 物理记录布局

```text
一个 4 KiB NOR 物理擦除块，共 16 页，每页 256 B

偏移 0x000 ┌──────────────────────────────────────────┐
           │ 第 0 页：组头 Header，256 B              │
偏移 0x100 ├──────────────────────────────────────────┤
           │ 第 1～14 页：7 个逻辑扇区，3584 B        │
           │ 每个逻辑扇区 512 B，占 2 个编程页        │
偏移 0xF00 ├──────────────────────────────────────────┤
           │ 第 15 页：提交记录 Commit，256 B         │
偏移 0xFFF └──────────────────────────────────────────┘
```

组头说明“我是谁、保存什么”；提交页说明“这个完整版本已经写完”。

| 字段 | 用途 |
| --- | --- |
| magic | 识别记录类型，避免把任意内容当成元数据 |
| format version | 判断盘上格式是否受当前软件支持 |
| epoch | 格式化代次，隔离不同次格式化的数据 |
| 逻辑组号 | 指明这块保存哪七个 LBA |
| 64 位组版本 | 同一 epoch、同一逻辑组的新旧顺序 |
| 七个扇区 CRC32 | 检查每个 512 B 数据扇区 |
| 头 CRC32 | 检查组头字段 |
| 提交中的头 CRC | 把提交页与具体组头绑定 |
| 提交自身 CRC32 | 检查提交记录是否完整有效 |

三个“版本”不能混淆：格式版本描述编码规则；epoch 随显式格式化更新；组版本随该组的写入更新。

当前格式按小端逐字段编码，不直接把 C 结构体写到 Flash，避免结构体填充、对齐和编译器布局影响盘上格式。元数据页最后 4 B 存 CRC，覆盖前 252 B；未使用字节填 0xFF。

### 6.2 映射关系如何计算

```text
group = LBA / 7              整数除法，得到逻辑组号
slot  = LBA % 7              得到组内第几个扇区

组内数据偏移 = 256 + slot × 512
```

例如：

```text
LBA 140～146 → group 20
LBA 147～153 → group 21

Map[20] = P_A
Map[21] = P_B
```

读 LBA 143 时：`group = 20`，`slot = 3`。先查 `Map[20]` 找到 P_A，再读取其数据区第 3 号扇区。

若内部映射索引 p 从“数据块 0”开始，分区开头还有两个卷描述块，则地址关系为：

```text
数据块在 FTL 分区内的起点 = (p + 2) × 4096
目标扇区在分区内的地址   = (p + 2) × 4096 + 256 + slot × 512
目标芯片地址             = FTL 分区基址 + 分区内地址
```

实际读取还需要按实现执行 CRC 检查和缓冲处理，不能把这个地址直接交给 APP 绕过 FTL。

### 6.3 为什么映射表是七分之一

同样数量的 512 B 逻辑扇区，如果逐扇区映射，需要每扇区一个映射项；现在每七扇区共用一个映射项，所以映射项数量是七分之一。

不是八分之一，因为 4 KiB 中有 512 B 用于头和提交，实际载荷只有七个扇区。

```text
单块载荷效率 = 3584 / 4096 = 87.5%
```

这还没有扣除卷描述块、预留空间和 FAT 文件系统本身的开销。

## 7. 一次写入怎样完成：先保留旧版，再提交新版

### 7.1 修改一个已经存在的逻辑扇区

假设 group 20 当前保存于 P_A，版本为 8。现在需要修改其中的 LBA 143：

```text
写入前：Map[20] → P_A，version = 8

P_A： [140] [141] [142] [143旧] [144] [145] [146]
```

FTL 执行以下步骤：

1. 读取旧组并检查数据，保留其他六个扇区。
2. 在内部工作区更新 LBA 143 的 512 B，组成完整的新组内容。
3. 找到一个已经确认擦除的空闲物理块 P_C。
4. 生成新组头：相同 epoch、group 20、version 9，以及各项 CRC。
5. 向 P_C 写组头和数据页，每页等待芯片完成。
6. 回读检查组头和完整数据。
7. 最后写提交页，等待完成并回读验证。
8. 把 RAM 映射改为 P_C，将 P_A 分类为旧失效块，之后才报告该组完成。

```text
写入后：Map[20] → P_C，version = 9

P_C： [140] [141] [142] [143新] [144] [145] [146]  当前有效
P_A： [140] [141] [142] [143旧] [144] [145] [146]  旧版，可回收
```

这叫写时复制或异地更新（Copy-on-Write）。核心是：**新版本可靠提交之前，不擦旧版本。**

同一笔底层请求里对同一个组的修改可以合并处理；完整覆盖七个扇区时，可以省略读取旧组。首版没有跨多个已完成写请求长期积攒的 FTL 写回缓存。

### 7.2 如果应用只写 100 B 呢

假设是在已有文件的某个扇区中间修改 100 B，且不跨扇区：

```text
应用修改 100 B
    ↓
FatFs 维护包含这 100 B 的 512 B 扇区，保留其他字节
    ↓ 在需要落盘时发出扇区写请求
FTL 更新该扇区所在的完整 3584 B 逻辑组
    ↓
为新组版本分配一个 4096 B 物理块
```

修改量小，不代表物理写入量小。若这次需要写满头、数据、提交，共有 16 页；全 0xFF 数据页可以跳过，具体编程量可能减少。另有校验读取、文件系统元数据更新，以及以后回收旧块的擦除成本。

这就是写放大：上层改动的字节少，底层为了保留其他数据、维护元数据和保证恢复，需要做更多读写。

### 7.3 为什么有些位置全 0xFF，也不原地补写

即使旧组某些数据页仍是 0xFF，组头里的 CRC 和最后的提交记录已经描述了一个完整版本。原地补写会改变这个版本的内容，却没有对应的新头和提交。

因此当前方案始终创建新的组版本。只有在一个已确认全块擦除的新块中，准备写入的某个数据页本来就是全 0xFF，才可以省略该页的编程；它仍参与 CRC 和回读检查。

### 7.4 数据很长，找不到连续的大空块怎么办

FTL 不需要为整个文件寻找一大片连续物理空间。

```text
文件逻辑内容 → 多个 FAT 簇 → 多个 LBA → 多个 FTL 组

group 20 → 物理块 100
group 21 → 物理块 237
group 22 → 物理块 81
```

每个组只需要一个完整、已擦除的 4 KiB 物理块，组与组之间可以不连续；读取时通过映射找回来。实际问题是有没有足够的可分配块，而不是能否找到与文件一样长的连续物理区。

一个跨组写请求按组依次提交。如果前面几个组已成功、后面一个组失败，前面已经提交的组不会自动回滚。

## 8. 读文件时，链路怎样反过来找到数据

假设应用读取文件偏移 5000 处的 100 B：

1. Service 检查文件句柄和挂载状态，交给 FatFs 执行读取。
2. FatFs 根据文件起始簇、簇链和文件偏移，找到对应逻辑扇区。
3. 若需要从介质读取，FatFs 经 DiskIO 发出 LBA 读请求。
4. FTL 根据 `LBA / 7` 查出当前物理块，根据 `LBA % 7` 定位扇区。
5. 底层读取数据，FTL 按实现校验相应数据，再向上提供逻辑扇区。
6. FatFs 取出应用需要的那 100 B，通过 Service 返回实际读取长度。

FatFs 可能命中自己的缓冲，并非每次 `f_read()` 都产生底层访问。读到文件末尾时，实际读取长度可能小于请求长度；调用者不能只检查返回状态而忽略长度。

### 8.1 从未映射的逻辑扇区返回什么

当前 FTL 约定未映射扇区读出全 0xFF。FTL 直接在输出缓冲中填充，不必为它分配物理块，更不必先向 Flash 写一遍 0xFF。

但这只是块设备层的行为，不能据此推断“新文件没写过的所有位置必定读出 0xFF”。文件长度、扩展方式、FatFs 缓冲处理以及原有逻辑扇区内容，都属于另外的语义。

尤其在删除后没有 TRIM 的情况下，那些 LBA 仍有映射，读原始逻辑扇区可能看到旧文件内容，并不会因为 FAT 簇已空闲就自动返回 0xFF。

## 9. “写成功”和“同步成功”分别意味着什么

### 9.1 至少有四个不同的完成点

```text
① 数据已经复制到某个 RAM 缓冲
② QSPI/MDMA 已完成一次数据传输
③ NOR 已完成内部编程或擦除，WIP 清零
④ FTL 新组已校验并提交，或者 FatFs 文件已完成所需同步
```

这些事件不是同一个时间点。

数据通过 QSPI 送到芯片，不代表芯片内部编程已经结束；一个数据页编程结束，也不代表整个 FTL 组的其他页和提交页已经完成。

### 9.2 首版没有 FTL 的 RAM 写回缓存

当前 FTL 不会仅把写请求拷到 RAM，就向块设备上层返回成功。

对一个底层逻辑写请求，成功要求涉及的组完成新版本提交及验证。也就是说，FatFs 收到这次 `disk_write()` 成功时，这次交给 FTL 的数据已经完成了底层持久化流程。

但 **FatFs 还可能保留没有发给 `disk_write()` 的内容和元数据**。所以这不能推导出“每次 `f_write()` 返回后，整个文件状态都已经持久化”。

### 9.3 f_write、f_sync、f_close、CTRL_SYNC 的区别

| 操作 | 主要含义 | 当前链路下要注意 |
| --- | --- | --- |
| `f_write()` | 写入文件内容，更新文件对象状态 | 可能直接发起底层写，也可能先修改 FatFs 缓冲；检查实际写入字节数 |
| `f_sync()` | 同步一个仍打开的文件 | 写出必要的脏数据和文件元数据，最终走设备同步 |
| `f_close()` | 同步后关闭文件对象 | 写文件关闭也可能等待、失败，必须检查结果 |
| `disk_ioctl(..., CTRL_SYNC, ...)` | 块设备同步契约 | 要求设备完成先前提交给它的写入；不能替 FatFs 写出尚在 FatFs 私有缓冲中的内容 |
| FTL Sync | 确认底层请求完成和设备安全状态 | 不要求把全部旧失效块都 GC 完 |

`f_sync()` 的参数是打开的 `FIL` 文件对象，不是路径，也不是“把所有文件、所有层的缓存一键刷新”的通用命令。APP 在本工程中通过 `Service_Filesystem_SyncFile()` 使用它。

### 9.4 为什么不能说最耗时的一定是 f_sync

大块写入时，`f_write()` 本身可能已经进行了大量页编程、回读校验和必要 GC。最后的 `f_sync()` 可能只需要处理剩余缓冲及少量元数据。

反过来，如果此前多数内容都积在上层缓冲中，`f_sync()` 也可能承担明显的写入成本。

```text
文件保存时间 = 多次 f_write 的耗时
             + 必要的 f_sync / f_close 耗时
             + 其他文件操作和上层处理耗时
```

评估保存性能时应该观察完整保存过程，不能只测 `f_sync()`，也不能在最后同步之前就宣称已测得完整持久写入速率。

## 10. 同步等待：存储任务停在哪里，CPU 又在做什么

### 10.1 “同步”描述调用者何时拿到结果

存储任务调用同步文件接口后，要等该接口返回才能继续执行后面的代码：

```text
StorageTask
    调用 Service 写文件
        ↓
    进入 FatFs 和底层写入流程
        ↓
    等待所需硬件操作完成
        ↓
    Service 返回状态和实际写入长度
        ↓
    StorageTask 执行下一句
```

这不等于 CPU 一直原地空转。Service 等待硬件事件时可以使 StorageTask 阻塞，让 FreeRTOS 调度其他就绪任务。

```text
时间 ─────────────────────────────────────────────→

StorageTask：提交页 ── 阻塞等待 ── 被唤醒、检查 ── 提交下一页
其他任务：             可以运行
Flash：               内部编程
中断：                              通知完成事件
```

不过，当前部分底层命令或页数据发送仍有 HAL 轮询，软件状态推进和 CRC 也需要 CPU。不能把整条路径描述成完全零 CPU 占用。

### 10.2 底层异步状态机与上层同步接口可以同时存在

底层通过 `Start` 发起，通过 `Process` 推进：

- `Start` 成功：请求被接受，不等于已经写完。
- 还有纯软件步骤：继续调用 `Process`，必要时让出调度。
- 等待硬件：Service 等待通知，并安排超时重查。
- 操作完成：Service 取得最终结果，再返回给 FatFs。

```text
同步执行器的概念流程

Start 接受请求
    ↓
Process
    ├── 可继续软件步骤 → 继续推进，适时让出 CPU
    ├── 等待硬件     → 阻塞等通知/超时重查 → 再 Process
    ├── 成功结束     → 返回成功
    └── 失败         → 安全收尾 → 返回错误或保持隔离
```

不能看到“忙”就一律睡眠，因为下一步也许只是计算 CRC 或更新索引，并没有任何硬件中断会唤醒任务。

### 10.3 中断通知只是提醒，不是最终结果

```text
硬件 IRQ
    ↓
HAL / IRQ Adapter 记录事件
    ↓
Platform 已注册的回调
    ↓
Service 通知 StorageTask
    ↓
StorageTask 在普通上下文继续 Process
    ↓
完成 Cache 收尾、状态检查和下一步操作
```

ISR 不执行文件操作、GC、FTL 提交或日志输出，也不在里面处理整块数据。一次通知可能对应一个原始页操作，不一定是整个文件请求完成。

通知可能迟到、合并或丢失，所以任务醒来后要检查状态机；没收到通知也要有重查机制。当前 StorageTask 通知索引 0 用于 SD 检测，1 用于 SD 传输，2 用于 Flash。

### 10.4 超时为什么不等于可以立即返回

若超时时 DMA 仍在访问缓冲，函数就返回并让调用者复用缓冲，会造成内存被继续读写。

因此必须先确认控制器和 DMA 不再访问相关内存。控制器 Abort 也不一定能取消已经送进 NOR 的内部编程/擦除；恢复时还要确认芯片 WIP 清零等状态。

当前配置的读、写、维护超时是软件策略，不是整个函数最长响应时间的绝对保证。如果硬件始终不能安全停止，就需要保持隔离，由板级看门狗或系统复位策略处理。

## 11. 最关键的区别：三种“空闲”不是同一个状态

| 说法 | 精确含义 | 是否马上能交给 FTL 写新版本 |
| --- | --- | --- |
| FAT 簇空闲 | 文件系统允许把该簇分配给新文件 | 不能据此判断；下面的 LBA 可能仍映射旧数据 |
| FTL 旧块失效（STALE） | 该物理块不再承载当前有效组版本，可以回收 | 不能，通常还没有擦除 |
| FTL 已擦除空闲块（FREE） | 已确认全块擦除，可以分配一个新组版本 | 可以，但要满足空闲保护下限 |

还要单独理解“未映射逻辑组”：它表示这个组没有已提交的物理版本，而不是某个特定物理块为空。读这种组返回 0xFF。

```text
文件系统簇空闲      是文件分配状态
FTL 旧版本失效      是物理记录的新旧关系
FTL 物理块 FREE     是经过验证的可编程状态
```

这三套信息分别用于回答三个问题：

1. 新文件可以使用哪些逻辑空间？
2. 哪些旧物理记录已经不需要保留？
3. 哪些物理块现在可以安全接收新版本？

## 12. 具体例子：删除一个 4 KiB 文件后，到底发生了什么

### 12.1 先约定这个例子的布局

这是人为选定的示意卷：每个 FAT 簇含 8 个扇区，数据区从 LBA 140 开始。FAT 数据簇从簇号 2 开始，因此簇 2 对应 LBA 140～147。实际盘上的数值由格式化结果决定。

有一个文件 `old.bin`，长度恰好 4096 B，占用簇 2：

```text
目录项：old.bin，起始簇 2，长度 4096 B
FAT[2] = 簇链结束标记

簇 2：LBA 140 141 142 143 144 145 146 147
```

它在 FTL 中跨两个组：

```text
group 20：LBA 140～146 → P_A，七个扇区都是 old.bin 的内容
group 21：LBA 147～153 → P_B，只有 LBA 147 属于 old.bin
                                      148～153 可能是其他文件的数据
```

下面 P_A、P_B、P_C、P_D 都是数据物理块，与后文格式化使用的卷描述块 VOL_A/VOL_B 无关。

### 12.2 第一步：关闭文件，再删除

应用在 StorageTask 中调用 Service 删除接口，Service 内部执行 `f_unlink()`。当前文件服务要求先关闭打开的文件。

FatFs 主要修改：

```text
目录：old.bin 的目录项被标记删除
FAT ：FAT[2] 从簇链结束标记改成空闲标记
```

FatFs 的空闲标记是 FAT 表中描述分配状态的值，不是把 LBA 140～147 的内容清零。

当前 `_USE_TRIM = 0`，后端也没有 `CTRL_TRIM` 实现。因此删除之后：

```text
文件系统视角：
    old.bin 不存在
    簇 2 可以分配给新文件

FTL 数据映射视角：
    Map[20] 仍然指向 P_A
    Map[21] 仍然指向 P_B
    P_A、P_B 仍是各自组的当前有效版本

物理内容视角：
    old.bin 原来的字节仍然存在
```

**这时不能 GC 掉 P_A/P_B。** FTL 没有收到“这些数据 LBA 可以丢弃”的契约信息；尤其 P_B 中还可能有其他文件的内容。

### 12.3 第二步：删除状态怎样保存到 Flash

目录项和 FAT 表的改动本身也要写逻辑扇区，因此会走：

```text
删除 old.bin
    ↓
修改目录项、FAT[2]
    ↓
写目录/FAT 所在的逻辑扇区
    ↓
FTL 为这些元数据所在组创建并提交新版本
    ↓
对应的旧元数据物理版本变为 STALE
```

为了让例子清楚，假设这些元数据位于另外的 FTL 组。真实布局也可能共享某些组，但仍须保留组内未修改的数据，原理不变。

所以删除确实可能导致 FTL 产生新的失效块，但这里失效的是 **目录/FAT 更新所替换的旧组版本**，不能据此推断文件数据对应的 P_A/P_B 已失效。

### 12.4 第三步：新文件重新使用簇 2

稍后创建 `new.bin`，假设 FatFs 恰好把刚空闲的簇 2 分配给它，并写满 4096 B。分配器不保证一定选这个簇，这里只是为了展示复用过程。

FatFs 再次写入 LBA 140～147，FTL 分别处理两个组：

```text
group 20：
    七个扇区全部替换为 new.bin 的内容
    新版本写到 P_C 并提交
    Map[20] → P_C
    P_A → STALE

group 21：
    替换 LBA 147
    保留 LBA 148～153
    新版本写到 P_D 并提交
    Map[21] → P_D
    P_B → STALE
```

P_B 能整块失效，是因为它里面所有仍需保留的数据都已经被带到新版本 P_D；不是因为删除文件允许把其他六个扇区一起丢掉。

若新文件只写了部分数据，只有实际涉及并提交了新版本的组会替换旧映射，不能把未改写的组也算作已经失效。

### 12.5 第四步：GC 回收 P_A/P_B

```text
FTL 找到 P_A：它已经是旧版本，不承载当前映射
    ↓
执行 4 KiB 擦除，等待 NOR 完成
    ↓
完整检查擦除结果
    ↓
P_A → FREE，空闲块计数增加
```

P_B 同理。回收后的块可以用于任意逻辑组的新版本，不限定给 `new.bin` 或 group 20/21。

### 12.6 把四个时刻放在同一张表里

| 时刻 | FAT 簇 2 | group 20 当前映射 | group 21 当前映射 | P_A/P_B 状态 |
| --- | --- | --- | --- | --- |
| 删除前 | 属于 old.bin | P_A | P_B | VALID |
| 删除成功后 | 空闲 | P_A | P_B | 仍 VALID |
| 新文件写满并完成相关提交后 | 属于 new.bin | P_C | P_D | STALE |
| GC 擦除并验证后 | 属于 new.bin | P_C | P_D | FREE |

这里忽略了其他元数据组和其他后台操作，只关注这两个数据组。

**删除释放文件系统空间；后续逻辑覆盖使旧物理版本失效；GC 把失效块变成可编程空闲块。** 当前工程不能把这三步合并描述成“删除文件就是把 FTL 块标废”。

## 13. 删除后需要再调用 f_sync 吗？掉电会不会丢失删除状态？

### 13.1 当前 f_unlink 的成功路径已经同步

已核对工程内 `Middlewares/Third_Party/FatFs/src/ff.c`，当前 `f_unlink()` 的相关成功路径为：

```text
dir_remove()            修改目录项
    ↓
remove_chain()          释放 FAT 簇链
    ↓
sync_fs()               同步文件系统元数据
    ├── sync_window()   写出脏窗口
    └── CTRL_SYNC       确认底层设备同步
    ↓
返回 FR_OK
```

因此，在当前实现和底层正确履行同步契约的前提下，**删除成功返回后，不需要再对这个已删除文件调用一次 `f_sync()` 才使删除生效。** 文件已经关闭并删除，也没有可供这样同步的有效打开文件对象。

前面“FAT 先在 RAM 改动，再写回介质”的通用描述仍然成立，但本工程 `f_unlink()` 已经在内部完成所需同步，不能遗漏这一点。

### 13.2 掉电时机仍然重要

| 掉电时机 | 应怎样理解 |
| --- | --- |
| 删除尚未开始 | 文件仍按原来状态存在 |
| 删除过程中 | 目录、FAT 等可能只完成部分更新，不能承诺整个删除原子完成 |
| 成功返回后，且介质满足约定故障模型 | 删除所需元数据已完成同步；重新挂载应看到删除结果 |
| 底层可能已提交，但上层因超时等返回失败 | 结果不确定；失败不能证明删除完全没发生 |

这里的风险不是“FTL 映射放 SDRAM，所以一掉电就忘记 FAT 簇空闲”，因为修改后的 FAT 表已经作为数据保存在 Flash 中。风险在于多笔文件系统更新还没全部完成就掉电。

### 13.3 普通删除不是安全擦除

目录项消失、FAT 簇释放，并不保证旧内容无法通过原始介质读取恢复。

FTL 异地更新还可能保留多个物理旧版本。即使从文件路径覆盖某段内容，也不能保证旧物理版本立即消失。

因此 benchmark 结束后的“清理测试文件”，指正常关闭和删除文件、释放文件系统占用，不是全盘擦除，也不是机密数据销毁保证。

## 14. GC 应归谁负责，怎样在后台推进

### 14.1 GC 是 FTL 的职责

GC（Garbage Collection）在这里表示回收不再有效的物理记录。

只有 FTL 掌握哪个组的哪个版本仍有效，因此由 FTL 选择可回收块。FatFs 不认识这些块，StorageTask 也不应自己指定某个物理地址进行回收。

```text
StorageTask 发现维护机会
    ↓
Service_Filesystem_MaintainFlash()
    ↓
Platform 发起 FTL 维护
    ↓
FTL 判断水位，选 STALE 块
    ↓
RawOps → Bridge → W25Qxx 擦除
    ↓
中断通知，Service 在普通任务中继续推进
    ↓
FTL 回读验证，更新 FREE 状态与计数
```

### 14.2 本方案的 GC 为什么不用先搬有效数据

一个组版本独占整个物理擦除块。新版提交后，旧块里的整组数据都被新版替代，旧块可以整体失效。

因此普通 GC 不必在一个混杂“部分有效、部分失效”的块里挑出有效页再搬迁。代价是每次局部修改都要创建完整新组，产生写放大。

这是一项设计取舍：把更新成本放到前台组写入，让普通回收流程更简单。它不是所有 FTL 都具有的性质。

### 14.3 后台 GC 与前台 GC

后台维护用于提前积累已擦除空闲块：StorageTask 默认约每 100 ms 有一次维护机会，一次维护最多擦一个可回收块。

“100 ms”是安排维护机会的周期，不是保证单块擦除在 100 ms 内结束。正在进行的 NOR 擦除也不能承诺随时抢占。

如果写入到来时空闲块已触及保护下限，则先在前台回收，再继续写入。这样能保证正确性，但会增加本次写请求的等待。

```text
空闲较多：新写入直接申请 FREE 块
空闲下降：后台维护逐步擦旧块
空闲过低：前台写入先等必要 GC
没有可安全回收的块：返回空间不足，不能擦当前有效数据
```

GC 没有候选块时应结束当前维护，不能忙循环，也不能为了达到高水位而牺牲有效数据。

### 14.4 当前默认水位怎么算

默认物理 FTL 分区是 24 MiB：

```text
物理块总数 N = 24 × 1024 × 1024 / 4096 = 6144
数据物理块 D = N - 两个卷描述块 = 6142
预留预算   R = ceil(D × 10%) = 615
逻辑组数   G = D - R = 5527

GC 启动水位 = ceil(R × 75%) = 462 块
GC 停止水位 = ceil(R × 90%) = 554 块
空闲保护下限 = 2 块
```

当已确认擦除的空闲块数 F 不高于 462，触发后台 GC；触发后，达到 554 才停止。两个水位形成滞回，避免刚擦一块就停、刚写一块又开。

这些 75%/90% 的分母是 **615 块预留预算**，不是整片 Flash，也不是当前失效块总数。两块只是紧急保护下限，绝不是正常后台 GC 要等到的低水位。

申请新块前，若 F <= 2，先回收；只有 F > 2 时才允许申请并扣减，不能越过下限。

### 14.5 预留空间不是一段固定物理地址

“预留 615 块”是限制可见逻辑容量，为异地写和回收留出周转空间。不是把某 615 个地址永久圈出来，其他地址一概不参与周转。

逻辑组的当前版本和空闲块会在整个数据块池中变化。

在逻辑组都已写过、没有在飞操作和故障块的简化情况下：

```text
6142 数据块 = 5527 当前有效块 + 615 个空闲或待回收旧块
```

覆盖写消费一个 FREE 块，同时让一个旧有效块变成 STALE；GC 再把 STALE 变回 FREE。

这也解释了为什么即使关闭 TRIM，反复删除并复用文件系统空间也不必天然越写越没空间：复用 LBA 时会替换旧组版本，预留预算为这个替换过程提供空间。GC 和错误处理仍必须正确，关闭 TRIM 也确实会让已删除数据继续占着有效映射。

### 14.6 GC 和磨损均衡不是同义词

当前分配游标、回收游标循环选块，能减少总盯着同一块操作的情况；但没有实现静态磨损均衡、冷数据搬迁或持久化擦除次数统计。

游标掉电会丢失，重新启动时恢复映射与块状态，再从初始化游标继续。这不影响数据定位正确性，但频繁重启可能造成磨损偏向。

本次上电的擦除计数不能当作芯片终身累计次数。实际寿命还与具体芯片型号、温度、擦除分布和写放大有关，不能仅凭“用了 GC”就承诺全盘磨损均匀。

## 15. 写到一半掉电，为什么还能找回正确版本

### 15.1 用组版本 8 → 9 看掉电窗口

假设 P_A 中 version 8 是已确认有效的旧记录，正在 P_C 中写 version 9：

| 掉电位置 | P_C 的情况 | 重启后怎样处理 |
| --- | --- | --- |
| 尚未写 P_C | 空闲或还未分配 | 使用 P_A 的 version 8 |
| 头或数据只写了一部分 | 没有有效提交记录 | 不把 P_C 当作新版本，使用 P_A |
| 数据已写完，但提交页还没写 | 数据看起来完整，仍未提交 | 仍使用 P_A |
| 提交页写到一半，CRC 无效 | 提交不可验证 | 按未提交处理 |
| 提交完整有效，但 RAM 映射还没改 | Flash 中已存在完整 version 9 | 扫描选择 version 9，重建映射到 P_C |
| RAM 映射已改、操作已成功返回 | P_C 是新当前版本 | 重启后仍选择 P_C |
| 后来 GC P_A 时掉电 | 旧块可能只擦了一部分 | 保留 P_C；旧块不能未经验证直接当 FREE |

这个表依赖约定故障模型：提交与校验规则能识别相应的撕裂操作，已完成持久写不会被之后的无关操作任意破坏。它不是对任意欠压、电气损伤的绝对保证。

### 15.2 为什么 RAM 映射还没更新也不要紧

组头和提交记录已经在 Flash 中写明：

```text
epoch = 当前格式化代次
group = 20
version = 9
提交绑定正确，数据校验通过
```

启动扫描不依赖上次 RAM 中的 `Map[20]`，而是重新寻找同一组的最高有效提交版本。

因此不会出现“新数据已经写完，但因为映射只存在 SDRAM，掉电后永远找不到”的问题。

### 15.3 不需要回写旧块的失效标记

旧块是否失效可以由新旧版本关系推导：同一 epoch、同一组存在更高的有效提交版本时，旧版本就不是当前版本。

运行中先在 RAM 标记旧块 STALE；重启后通过扫描重新得到这个结论。不需要冒险再去旧块里补写一个“无效”字节。

### 15.4 校验失败为什么不一律退回旧版本

要区分两类情况：

- **没有有效提交的新尝试**：可能写到一半，不应成为当前版本。
- **已经有效提交的最新版本，其数据或绑定信息损坏**：应报告损坏，不能悄悄返回更旧的数据。

第二种情况如果静默回退，可能让已经成功保存的设置、计数或文件系统元数据无声倒退。当前实现宁可明确报错，也不把损坏伪装成成功读取旧值。

提交页本身 CRC 无效时，当前方案按未提交处理，无法完美区分“当时没写完”和“后来提交页损坏”。CRC 也存在碰撞可能。因此这里的提交规则是特定故障模型下的恢复机制，不是数学意义上对所有损坏都绝对可靠的原子存储器。

### 15.5 FTL 单组提交不等于整文件事务

一个文件操作可能修改数据、FAT 表和目录；即使每个组都是完整旧版或完整新版，也可能出现：

```text
文件数据组：新版已提交
FAT 表组  ：新版已提交
目录项组  ：还没更新就掉电
```

每组单独看都完整，文件系统整体却可能处于中间状态。删除、创建、扩展文件同样可能跨多个组。

所以：FTL 负责底层组记录的恢复；FatFs 负责文件系统格式；上层若需要“整份配置要么全旧、要么全新”的更强保证，还需要另行设计并验证应用提交协议。首版没有承诺整文件事务，也没有实现文件系统日志。

## 16. 上电后如何从 Flash 重建映射和块状态

### 16.1 SDRAM 表是运行时索引，Flash 记录才是恢复依据

```text
Flash 持久内容
    卷描述、epoch、各组版本、数据、提交、CRC
             ↓ 上电扫描和校验
SDRAM 运行时表
    Map[group]、Versions[group]、BlockStates[physical_block]
```

这些 SDRAM 表不是从 Flash 的某张完整表原样拷贝出来，而是根据记录逐项重建。首版没有依赖一份需要频繁原地更新的持久映射表。

即使链接段使用 NOLOAD，启动也不能相信其中残留数据。复位后的 RAM 内容不构成可靠持久状态，重新打开卷必须初始化并重建。

### 16.2 实际扫描做什么

1. 读取两个卷描述块，验证格式、几何、epoch 和阶段。
2. 遍历数据区的每个物理块，读取组头页和提交页。
3. 根据有效提交中的 epoch、组号和版本，选择每组最新候选。
4. 头和提交页都像空白的块，还要读取整块，确认全块 0xFF，才计入 FREE。
5. 对最终选中的每个组版本，读取完整 4 KiB，校验头、数据和提交绑定。
6. 完成映射、版本、块状态和空闲计数，才把卷置为就绪。

旧失效块可能在 GC 中被擦掉头部、却残留提交页。恢复先按提交关系挑选最新版本，再验证最终选中的记录，避免把旧块的撕裂擦除错误当成当前有效数据损坏。

### 16.3 是不是“每次把整个逻辑区读一遍”

更准确的说法是：**遍历整个 FTL 数据物理块范围，读取元数据，并按分类进一步读取数据。**

默认 6142 个数据块，仅头页和提交页就约读 3 MiB；如果 5527 个逻辑组全都有映射，完整记录验证约读 21.6 MiB，另有空白候选块验证等读取。

总读取量取决于介质状态，甚至可能超过分区容量，因为某些元数据先读一次，完整验证又读一次。这些是字节数估算，不是启动耗时实测。

扫描只保留索引表并复用工作区，**不会把整片 24 MiB 分区全部常驻到 SDRAM。**

### 16.4 当前内存安排

| 内容 | 当前安排 | 是否依赖掉电保留 |
| --- | --- | --- |
| Map | SDRAM 中的物理块索引表 | 否，扫描重建 |
| Versions | SDRAM 中的每组 64 位版本表 | 否，扫描重建 |
| BlockStates | SDRAM 中的每物理块 8 位状态 | 否，扫描重建 |
| 组工作区 | 4096 B，内部 SRAM，32 B 对齐 | 否，只在当前操作期间使用 |
| 校验工作区 | 512 B，内部 SRAM，32 B 对齐 | 否 |

当前 Platform 按数据物理块容量预分配 Map/Versions，而不是仅按实际逻辑组数紧凑分配。默认三张表合计 79,872 B，约 78 KiB，不包含句柄、统计和两个工作区。

同时最多一个 FTL 操作，工作区由 Platform 长期持有并注入 FTL，不在任务栈上临时放一整组数据。

### 16.5 可选日志用来观察什么

`FILESYSTEM_FLASH_DIAG_LOG_ENABLE` 控制启动摘要，默认关闭。可以输出格式版本、epoch、有效组数、确认擦除的空闲块数、失效块数及扫描耗时。

这些日志帮助观察恢复和空间状态，不是把每个扇区内容都打印出来。关闭可选摘要不应隐藏错误，也不改变提交或 GC 行为。

## 17. 为什么格式化要两个卷描述块

### 17.1 先区分两层格式化

```text
FTL 格式化
    建立卷描述、epoch 和几何，擦除并验证数据物理块
    得到可供读写的逻辑扇区设备
             ↓
FatFs 格式化
    在这个逻辑设备上写引导参数、FAT 表、目录等结构
    得到可以挂载和创建文件的 FAT 文件系统
```

只有 FTL 格式化完成，不代表 FatFs 已经有文件系统可挂载；反过来，`f_mkfs()` 也不负责建立这套底层 FTL 卷描述。

### 17.2 PREPARING 与 READY

分区前两个物理块专门保存卷描述，记作 VOL_A 和 VOL_B，不参与数据组分配。

每块用不同页分别记录：

- PREPARING：这个 epoch 的格式化已经开始。
- READY：该 epoch 的数据区已经全部擦除并验证完成。

READY 不是把 PREPARING 原地任意改几个 bit，而是在另一页追加记录，分别带 CRC。

### 17.3 重新格式化的顺序

假设原来有有效旧卷描述，过程为：

```text
保留 VOL_A 的旧有效描述
    ↓
擦除并验证 VOL_B，写新 epoch 的 PREPARING，回读验证
    ↓
在 VOL_A 也建立并验证相同新 epoch 的 PREPARING
    ↓
两份 PREPARING 都验证后，才开始破坏性擦除数据区
    ↓
逐块擦除并验证整个数据区
    ↓
追加 VOL_B READY，回读验证
    ↓
追加 VOL_A READY，回读验证
    ↓
两份 READY 都验证后，格式化调用报告成功
```

因此之前讨论的“B READY 后再写 A READY”是正确的，但前提是同一新 epoch 的两份 PREPARING 已建立，且数据区已经完成擦除验证。

### 17.4 格式化中途掉电如何判断

| 恢复时看到的情况 | 处理 |
| --- | --- |
| 只有旧代次的有效描述，没有可验证的新代次 | 根据有效旧描述处理 |
| 最新 epoch 只有 PREPARING | 判定格式化未完成，不让旧 epoch 的 READY 掩盖它 |
| 最新 epoch 的 VOL_B 已 READY，VOL_A 仍 PREPARING | 数据区格式化已完成，可以依据该 READY 恢复 |
| 同一最新 epoch 两份 READY 均有效 | 正常按该代次打开 |
| 格式或几何不兼容 | 报不兼容，不按新参数强行解释旧数据 |

“格式化函数还没来得及返回成功”和“介质上已经有可恢复的新卷”可以同时成立。不要用未收到成功推断介质未变化。

### 17.5 不自动格式化

挂载失败可能是未格式化，也可能是损坏、格式不兼容、I/O 故障或正在恢复。

当前工程不会在挂载失败时自动调用任何一层格式化，也不会看到 PREPARING 就自动续擦。格式化必须是显式的破坏性操作，先确认范围和已有数据。

## 18. SDRAM 大缓冲和 MDMA 能帮什么忙

### 18.1 大缓冲放在应用或 Service 数据组织这一侧

如果应用持续产生数据，可以考虑在 SDRAM 中准备较大的缓存，积累一批后通过 Service 写文件。

```text
数据生产者 → SDRAM 缓冲 → StorageTask → Service → FatFs → FTL
```

这样可能减少零碎调用，也给 FatFs 和 FTL 在同一请求内合并连续扇区提供机会。但实际请求仍可能因 FAT 簇边界、文件偏移等拆分，不能保证“一次大 f_write 就只更新每个 FTL 组一次”。

本工程首版还没有实现跨任务文件请求队列或上述通用 SDRAM 写缓存；字体、模型预加载到 SDRAM 也属于另外的上层资源方案。

### 18.2 缓冲大小解决突发，不能解决长期吞吐不足

若数据产生速度为 R B/s，存储可能连续 T 秒不能接收新数据，仅覆盖这段停顿就需要至少约 `R × T` 字节缓冲，还要给调度、波动和其他在途数据留余量。

但如果长期平均产生速度高于持久写入速度，再大的有限缓冲最终也会写满。

双缓冲能让一块缓冲交给存储任务时，生产者填另一块。前提是明确缓冲所有权：正在被消费的缓冲，在接口允许归还前不能改写或释放。同步调用成功或完成安全失败收尾后，调用者才能按契约复用。

### 18.3 RAM 缓存越多，未落盘数据可能越多

```text
应用 SDRAM 中待写的数据
    + FatFs 尚未写出的脏数据/元数据
    = 仍需考虑掉电丢失的上层状态
```

FTL 不提前报告 RAM 写成功，只能保证交给它并成功完成的底层请求，不能自动持久化应用还没提交的缓存。

同步策略要结合“能接受丢失多少时间的数据”与写入成本确定。例如周期同步和关键事件同步是上层策略，首版没有把这个决策强行固定为所有文件相同。

### 18.4 MDMA 搬数据，不代替 Flash 内部擦写

当前 QSPI 原始读取已接入 MDMA；页编程数据发送仍使用 HAL 轮询，不能宣称已经实现 MDMA TX。

即使以后加入发送 DMA，也仍然需要按页边界发命令、等待 WIP 清零、执行 FTL 校验和最后提交。把 32 KiB 缓冲一次交给 DMA，不等于 NOR 就能把它当成一个无限长的原子编程操作。

```text
DMA 传输完成 ≠ NOR 编程完成 ≠ FTL 组提交完成 ≠ 文件同步完成
```

### 18.5 Cache 和缓冲可达性

STM32H743 的 CPU Cache 与 DMA 访问需要协调。CPU 修改过的 Cache 内容可能尚未写回 RAM；DMA 写入 RAM 后，CPU 也可能仍读到旧 Cache。

硬件适配层要根据数据方向维护 Cache，检查 32 B 缓存行对齐与整行所有权，并确认选用的 RAM 能被相应 DMA 访问。不能只把一个数组移到 SDRAM，就默认这些条件全部满足。

当前 FTL 使用内部对齐工作区执行原始 DMA 读取，APP 文件缓冲不直接交给 DMA。Cache 原理可结合学习笔记中的《04_Cache原理.md》理解。

### 18.6 Memory-mapped 模式并不等于访问 FTL 文件

QSPI 的 memory-mapped 窗口展示的是芯片物理地址空间，里面包含组头、旧版本、提交页等，不是 FatFs 的连续文件视图。

当前 Platform 在整个 FTL 操作期间关闭映射模式，正常成功并确认硬件空闲后按进入时状态恢复；故障时保持关闭。不能在每页编程间隙随意恢复，也不能允许其他任务同时从映射窗口取资源。

若字体或模型需要持续访问，可以另行规划资源区和预加载策略，但必须遵守同一芯片的访问仲裁。

## 19. 容量与宏配置：哪些能调，哪些会改变盘格式

### 19.1 默认 24 MiB 为什么只能得到约 18.9 MiB 逻辑容量

根据第 14 节的块数：

```text
逻辑组数 = 5527
逻辑扇区数 = 5527 × 7 = 38689
逻辑容量 = 38689 × 512 = 19,808,768 B ≈ 18.9 MiB
```

原因包括两个卷描述块、10% 周转预算，以及每个 4 KiB 记录只有 3.5 KiB 数据。FatFs 再从逻辑容量中占用 FAT、目录等空间，所以实际文件可用容量还会少一些。

这里的“容量动态留”是通过宏配置和卷几何计算容量，不表示可以在已有数据上运行时任意扩缩分区。

### 19.2 当前主要配置项

| 配置项 | 默认值 | 调整影响 |
| --- | --- | --- |
| `PLATFORM_FLASH_FTL_SIZE_BYTES` | 24 MiB | 改变物理分区长度，当前基址随尾部边界向前计算 |
| `FLASH_FTL_RESERVE_PERCENT` | 10% | 改变可见逻辑组数量与周转预算 |
| `FLASH_FTL_GC_START_RESERVE_PERCENT` | 75% | 控制何时开始后台 GC，分母为预留预算 |
| `FLASH_FTL_GC_STOP_RESERVE_PERCENT` | 90% | 控制已启动 GC 何时停止 |
| `FLASH_FTL_MIN_FREE_BLOCKS` | 2 | 约束分配后的最低已擦除空闲块数量 |
| `FILESYSTEM_FLASH_DIAG_LOG_ENABLE` | 0 | 关闭可选诊断摘要 |
| `STORAGE_FLASH_MAINTENANCE_PERIOD_MS` | 100 ms | 提供后台维护机会的周期 |

这些宏分别放在所属模块的私有配置头中。方便维护者修改参数，不等于允许其他模块包含私有配置头并依赖其内部细节。

容量、预留比例会改变几何，不能只改宏就把已有卷按新容量解释。当前分区随大小改变基址，还要重新检查资源、镜像槽及诊断保留区，必要时迁移数据并显式重新格式化。

GC 水位和日志开关不改变组记录布局，但调整仍要满足相互约束并验证运行效果。

### 19.3 DiskIO 对 FatFs 报告什么

| 命令 | 当前默认返回 |
| --- | --- |
| `GET_SECTOR_COUNT` | 38689 |
| `GET_SECTOR_SIZE` | 512 B |
| `GET_BLOCK_SIZE` | 1 个逻辑扇区 |
| `CTRL_SYNC` | 经 Service 执行同步确认 |

`GET_BLOCK_SIZE = 1` 是给当前 FatFs 的逻辑对齐提示，不表示 NOR 可以擦除 512 B。七扇区组不是二次幂，且属于 FTL 内部约束，本实现不把它直接作为该提示返回。

## 20. APP 应该怎样使用当前 Service

### 20.1 启动链路

```text
SDRAM、QSPI、W25Qxx 等底层就绪
    ↓
Platform 绑定实例、分区、FTL 工作内存
    ↓
StorageTask 初始化 Service Flash 执行器
    ↓
OpenFlash：扫描并打开 FTL 卷
    ↓
MountFlash：通过 USERPath 挂载 FAT 文件系统
    ↓
文件操作、可选 benchmark、空闲维护
```

若有破坏性的 SDRAM 自检，必须早于 FTL 表或其他有效内容占用 SDRAM。SD 与 Flash 的就绪、挂载和错误状态独立，不能因其中一个成功就把另一个也当成成功。

FTL 已经打开就绪时，USER 初始化只检查状态，不重复扫描整个分区。

### 20.2 当前公开文件接口

| Service 接口 | 作用 |
| --- | --- |
| `Service_Filesystem_OpenFlashFile()` | 打开只读文件，或仅创建新文件 |
| `Service_Filesystem_ReadFile()` | 读取并返回实际字节数 |
| `Service_Filesystem_WriteFile()` | 写入并返回实际字节数 |
| `Service_Filesystem_SyncFile()` | 同步打开文件 |
| `Service_Filesystem_CloseFile()` | 关闭文件，成功后清空调用者句柄 |
| `Service_Filesystem_RemoveFlashFile()` | 删除文件，不删除目录 |

APP 只持有 `Service_Filesystem_FileTypeDef`，不持有 FatFs 的 `FIL`，也不直接调用 `f_unlink()`。

首版约束是唯一 StorageTask 上下文、已挂载 Flash 卷、同时最多打开一个文件。文件名只接受根目录下最长 31 字节的合法 ASCII 文件名，不接收卷号或路径分隔符。

只读和“仅新建”是当前公开模式，并不是完整文件管理 API。仅新建遇到同名文件返回忙，不截断、不覆盖。

### 20.3 一个正常保存流程的检查点

```text
打开/仅新建
    ↓ 检查状态
分批 WriteFile
    ↓ 每次检查状态，以及 transferred 是否等于本次请求长度
SyncFile
    ↓ 检查状态，确认本轮文件同步
CloseFile
    ↓ 检查状态，确认句柄已关闭
按业务需要保留文件，或调用 RemoveFlashFile 删除临时文件
```

短读可能是 EOF，短写可能是空间不足，`SERVICE_OK` 不能替代长度检查。

关闭失败时，当前 Service 保留文件槽和句柄，不伪造关闭成功；删除时只要仍有打开文件，就拒绝操作。不存在的文件在 Service 删除封装中按成功处理，这是封装的约定，不应误认为原始 `f_unlink()` 对不存在路径也必定返回成功。

### 20.4 故障恢复后不能继续用旧文件句柄

显式恢复会处理旧卷状态、确认硬件安全并重扫 FTL，之后由调用者重新挂载、重新打开文件。旧句柄和旧 FatFs 文件对象不能透明地继续写。

句柄代次检查用于拒绝关闭、重开或卷注销前遗留的旧句柄。当前没有跨任务文件队列，也不能从其他任务或 ISR 直接并发进入这条链路。

## 21. 文件 benchmark 验证什么，测完怎样清理

### 21.1 文件测试与原始 Flash 自检不同

原始自检验证指定保留区域的读写、擦除、QSPI/MDMA 等底层通路；文件 benchmark 验证完整的 APP → Service → FatFs → FTL → NOR 链路。

文件 benchmark 不自己选物理地址，也不在结束后调用某个固定地址的擦除函数。

当前文件测试默认总量 1 MiB、每次 4 KiB，临时文件名 `__ftlrw.bin`，实际卷路径由 Service 决定：

```text
仅新建测试文件
    ↓
按文件偏移生成确定性图样并分批写入
    ↓
同步 → 关闭
    ↓
重新只读打开 → 读取测速 → 关闭
    ↓
再次打开 → 逐字节验证图样并检查 EOF → 关闭
    ↓
删除本轮创建的测试文件
```

如果同名文件本来就存在，拒绝测试，不先删掉它。只有本轮确认创建的文件才进入清理范围。掉电后残留的同名文件也不会在下次启动自动删除。

### 21.2 耗时的边界

当前写速包含图样生成、写调用和最后同步；读速不包含逐字节内容比较，校验单独跑。打开、关闭、删除和日志不计入吞吐统计。

因此若要评估“整个保存任务用了多久”，还需要统计这些阶段；不能把文件 benchmark 吞吐直接当作 QSPI 总线带宽或 NOR 纯编程速度。

长文件测试用 RTOS tick 计时，避免直接使用 32 位 DWT 周期差统计长操作时遭遇回绕问题。结果仍包含调度与必要 GC 的影响。

### 21.3 清理失败不能假报成功

读写、同步或校验失败后也会尝试关闭和删除。但如果介质异常、关闭持续失败或删除失败，就可能留下文件，需要明确记录。

正常删除的验收是文件系统层面文件不再存在、占用簇得到释放；并不要求旧物理数据立即全被擦除，也不应为了测试收尾主动破坏 FTL 分区。

### 21.4 当前验证边界

截至本文核对时，主机测试覆盖正常流程、同名保护、短写、错误注入、关闭/删除失败等情形，相关回归共 16 项 CTest 通过。Fake NOR 和任务替身不能代替实际硬件的掉电、DMA/Cache、中断时序和性能测试。

文件 benchmark 总开关当前默认关闭。开启后会实际链接 CP936 字符转换表，现有正式链接布局下 Debug/Release 都存在第一内部 FLASH 区容量不足；Release 的布局草案已经验证，但正式链接调整尚待授权。因此不能把主机测试通过说成开启 benchmark 的正式固件已经可烧录。本次编写笔记不修改这些工程配置。

## 22. 容易混淆的问题对照

| 问题 | 应怎样理解 |
| --- | --- |
| 删除文件是不是 FTL 马上把数据块标废？ | 当前无 TRIM，不是；FAT 簇先释放，数据 LBA 的映射仍在 |
| 删除状态只在 RAM 里吗？ | 修改过程中可以有 RAM 脏状态；当前 f_unlink 成功前已同步元数据 |
| 删除成功后还要 f_sync 这个文件吗？ | 不需要；f_sync 面向打开文件，当前删除内部已走 sync_fs/CTRL_SYNC |
| FAT 空闲簇是不是已经全 0xFF？ | 不是，分配状态不代表物理内容 |
| STALE 块能直接写新数据吗？ | 不能，先擦除并验证，转为 FREE |
| 空白 Flash 是全 0 吗？ | 不是，是全 0xFF |
| 256 B 页是不是 FTL 分配单位？ | 不是，本方案分配完整 4 KiB 块 |
| 3.5 KiB 分组是否把逻辑扇区改成 3.5 KiB？ | 没有，FatFs 仍读写 512 B 扇区 |
| 4 KiB 记录的映射项是逐扇区方案的八分之一吗？ | 是七分之一，512 B 元数据不作为文件载荷 |
| 有一部分数据仍是 0xFF，就能在已提交组原地补写吗？ | 当前格式不允许，必须创建新组版本 |
| 写大文件需要连续物理空块吗？ | 不需要，每组通过映射定位一个完整空闲块 |
| f_write 不耗时，f_sync 才真正写吗？ | 两者都可能触发真实写入，取决于缓冲和请求 |
| 同步等待会让所有任务停住吗？ | 不会，硬件等待可阻塞 StorageTask，让其他任务运行 |
| 收到 DMA 完成中断就能认为文件写完吗？ | 不能，还可能有 NOR 内部操作、组提交及文件元数据同步 |
| FTL 映射放 SDRAM，掉电后是不是全丢了？ | RAM 表丢失，但由 Flash 上已提交记录重建 |
| 启动扫描是不是把整个盘加载进 SDRAM？ | 不是，保留表并复用工作区，按恢复算法读取校验 |
| GC 是 FatFs 的事情吗？ | 不是，FTL 判断可回收块，StorageTask 只提供维护机会 |
| FTL Sync 是否要擦掉全部旧块才返回？ | 不需要，持久化完成与回收空间是不同条件 |
| 单组掉电可恢复是不是整文件更新原子？ | 不是，文件及元数据可能跨多个组 |
| 挂载失败能自动格式化吗？ | 当前禁止，避免把故障或不兼容误当空盘 |
| 启用 TRIM 是否只需改一个宏？ | 不是，还需设计后端释放语义、部分组保留与掉电恢复 |

关于未来 TRIM：它可以让文件系统把“这些逻辑扇区不用了”传给块设备，但不能直接把跨组范围向外取整并擦除。例如只释放 LBA 147，仍需保留同组 148～153；释放信息也需要可恢复的设计。当前未实现，不应仅开启宏就宣称支持，更不应把 TRIM 等同安全擦除。

## 23. 用 STM32CubeProgrammer 烧录外部 NOR 固定资源

### 23.1 `.stldr` 是临时烧录算法，不是主固件

STM32CubeProgrammer 默认只理解 STM32 内部 Flash。要访问挂在 STM32H743 QSPI 上的 W25Q256，需要一个与具体 MCU、时钟、引脚和 Flash 命令匹配的 External Loader。

```text
CubeProgrammer
    ↓ 通过 ST-LINK/SWD 把 .stldr 临时下载到 AXI SRAM
STM32H743 执行 Loader 的 Init()
    ↓ 配置系统时钟、QSPI GPIO、W25Q256 和 Memory-mapped 模式
CubeProgrammer 访问 0x90000000～0x91FFFFFF
    ↓ 调用 SectorErase / Write / CheckSum / Verify
外部 32 MiB W25Q256
```

`.stldr` 不永久写入 MCU 内部 Flash，也不随主固件启动。主固件仍烧录到 `0x08000000`；Loader 只在生产、调试或资源更新时帮助 CubeProgrammer 访问外部 NOR。

本工程 Loader 位于：

```text
Tools/external_loader/
└── build/arm-gcc/W25Q256_STM32H743ZG.stldr
```

它直接访问物理 NOR，不经过 Filesystem Service、FatFs 或 FTL。正因为绕过了这些保护层，地址和擦除范围必须由操作者准确指定。

### 23.2 安装和首次读取验证

1. 完全退出 STM32CubeProgrammer。
2. 把 `W25Q256_STM32H743ZG.stldr` 复制到 CubeProgrammer 安装目录的 `bin/ExternalLoader/`。
3. 重新打开 CubeProgrammer，用 ST-LINK/SWD 连接开发板。
4. 在 **External loaders** 中勾选 `W25Q256_STM32H743ZG`。
5. 确认右侧连接信息已经显示该 External loader。
6. 在 **Memory & File editing** 中读取 `0x90000000`，长度先用 `0x10`。

能够读到已有数据或全 `0xFF`，才说明 Loader 初始化和 QSPI Memory-mapped 窗口已经打通。不能因为列表中能看到 Loader 名称，就推断 `Init()` 一定成功；列表内容来自 `.info` 中的 `StorageInfo`，硬件初始化要到实际读取时才会执行。

替换 `.stldr` 后必须重启 CubeProgrammer。程序可能继续使用当前会话已经缓存的旧算法，仅覆盖安装目录中的文件不会刷新它。

普通 STM32 ROM DFU 不会执行这个面向 ST-LINK/SWD 的 External Loader。若以后需要通过 USB 更新外部资源，应由主固件提供独立升级协议和分区保护，而不是把 `.stldr` 当作 DFU 镜像。

### 23.3 本次 `Data read failed` 的原因和修复

本次现象为：内部 Flash `0x08000000` 正常可读，External loader 已勾选，但读取 `0x90000000` 稳定返回 `Data read failed`。

主工程与 Loader 的 25 MHz HSE、PLL、QSPI 分频、容量和六个 GPIO 已逐项核对一致。最终问题发生在 Loader 建立系统时钟的阶段：

```text
SystemInit 后：Cortex-M7 使用约 64 MHz HSI
    ↓
HAL_RCC_OscConfig 等待 HSE/PLL，并依赖 HAL_GetTick 判断超时
    ↓
旧实现尚未启用 DWT，却让 HAL_GetTick 每被调用一次就增加 1
    ↓
100 ms 被错误压缩成约 101 次高速循环
    ↓
HSE/PLL 尚未稳定便被判超时，Init() 返回 0
    ↓
0x90000000 未建立映射，CubeProgrammer 报 Data read failed
```

修复后，`SystemInit()` 返回便先按 64 MHz 启用 DWT 真实时基；PLL 切换完成后，再按 480 MHz 重新建立每毫秒周期换算。重新构建、替换 Loader 并重启 CubeProgrammer 后，`0x90000000` 已在实际硬件上成功读出。

这个问题说明：外部 Loader 即使不运行 RTOS，也必须为 HAL 的超时轮询提供与真实时间近似一致的单调 tick。把“函数调用次数”当成毫秒，会让所有依赖 HAL timeout 的初始化产生与 CPU 速度相关的误判。

### 23.4 固定资源包布局与烧录参数

当前 CP936 双向转换表和默认壁纸已经打包为：

```text
build/external-resources/resource_pack.bin
```

它位于外部 NOR 的固定原始资源区，不属于 FatFs 文件，也不经过 FTL：

| 项目 | 数值 |
| --- | --- |
| W25Q256 Memory-mapped 基址 | `0x90000000` |
| 资源包芯片物理偏移 | `0x00401000` |
| CubeProgrammer 烧录地址 | `0x90401000` |
| 资源包长度 | `0x65000`，即 413696 B |
| 最后一个占用地址 | `0x90465FFF` |
| 结束地址（不含） | `0x90466000` |
| 文件魔数 | `RPK1`，字节 `52 50 4B 31` |

资源头中记录的当前内容为：

| 资源 | 包内偏移 | 长度 | CRC32 |
| --- | ---: | ---: | --- |
| `uni2oem` | `0x1000` | 87172 B（`0x15484`） | `0xFBAAB4D2` |
| `oem2uni` | `0x16484` | 87172 B（`0x15484`） | `0x60F7F8F0` |
| 默认壁纸 | `0x2C000` | 230400 B（`0x38400`） | `0xBBB21D5D` |

CubeProgrammer 按 32 位小端整数显示文件时，开头会看到 `314B5052`。这与字节顺序 `52 50 4B 31` 是同一内容，不是魔数写反。

### 23.5 实际烧录与验收步骤

在 Loader 首次读取验证通过后：

1. 打开 `resource_pack.bin`。
2. 下载地址填写 `0x90401000`，不能填文件视图自己的偏移 `0`，也不能填整个芯片窗口基址 `0x90000000`。
3. 勾选写后校验。
4. 不使用 **Full chip erase**，防止清除 FTL、诊断区或其他已有分区。
5. 不使用 **Run after programming**；资源包不是可执行程序。
6. 下载完成后，从 `0x90401000` 回读，确认魔数、长度和三个 CRC 与上表一致。
7. 需要更严格确认时，使用 CubeProgrammer 的 **Verify** 将外部内存与原始文件逐字节比较。

本次实际硬件回读已经确认：地址为 `0x90401000`，魔数为 `RPK1`，包长度为 `0x65000`，三个资源 CRC 与打包输出一致。至此只能证明“PC → Loader → QSPI NOR”的烧录链路正确；主固件启动后仍应检查资源头和 CRC，并验证 CP936 转换与默认壁纸的实际读取路径。

### 23.6 与 FTL 分区的边界

固定资源区和 FTL 都位于同一颗 W25Q256，但用途与访问路径不同：

```text
固定资源：主固件按已约定物理地址读取，CubeProgrammer 可离线更新
FTL 区域：只能通过 FTL 的逻辑扇区接口读写，由 FTL 管理映射、提交和 GC
```

当前资源包结束于芯片偏移 `0x00466000`；默认 FTL 起点为芯片偏移 `0x007FF000`，两者不重叠。以后调整资源包大小、FTL 容量或尾部分区时，必须重新做区间检查，不能只看当前镜像能够写入。

在主固件运行期间，同一 QSPI 控制器还涉及 Memory-mapped 模式与间接擦写模式切换。资源读取必须服从 Platform/驱动的访问仲裁，不能在 FTL 擦写期间由另一个任务无保护地访问映射窗口。
